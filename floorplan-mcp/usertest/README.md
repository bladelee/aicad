# V3 真人用户测试包 — floorplan-mcp

> **用途**：Phase 1 MVP 完成后，拉 3-5 个真实设计师做 30-45 分钟用户测试，输出量化评估决定是否进 Phase 2。
> **依据**：`../../产品Spec.md` §3.0（角色画像）+ §4（V3 三阶段）+ §13（Phase 1 自检）
> **包含文件**：
>   - 本文件：主持（招募）指南 + 跑测流程
>   - `task-card.md`：参与者任务书（打印/发给参与者）
>   - `scorecard.md`：单场量化打分表（每场一份）
>   - `aggregate.md`：多场汇总表 + 通过判定

---

## 0. 谁来跑这测（招募）

### 0.1 招募画像（产品Spec §3.0）

| 画像 | 必招人数 | 关键特征 | 招募渠道 |
|------|---------|---------|---------|
| **P1 室内设计师**（主） | 2-3 | 会 CAD、看懂 DWG 图层/块；不写代码 | 设计公司朋友/认识的设计师 |
| **P2 装修施工/包工头** | 1 | 看 CAD 图、量尺寸；技术背景浅 | 装修队/包工头朋友 |
| **P3 懂 DIY 的房主**（可选） | 0-1 | 不熟 CAD、能装 Docker | 网上/同事 |

**最低门槛**：3 人（≥2 个 P1 + 1 个 P2）。少于 3 人信号不足。

### 0.2 排除标准（不要招这些人）

- ❌ 写过 Python / 学过 FreeCAD API 的人（太懂会偏开发视角，不能反映真实摩擦）
- ❌ 测试前一两周用过 Claude Code / Cursor 等 AI 编程工具的人（掩盖 MCP 学习成本）
- ❌ 没装过 Docker 的 P2（除非测试机已装好；P2 自己装 Docker 超出 15 分钟）

### 0.3 报酬与时间

- 时长：30-45 分钟/人
- 报酬：50-100 元礼券/杯咖啡 + 测试结果反馈（建议）
- 形式：现场或远程共享屏幕（远程要能看到参与者操作 Goose/OpenWork）

---

## 1. 测试前置（主持人准备清单）

测试前主持人必须准备好（每场都重新检查）：

- [ ] Phase 1 自检（产品Spec §13）全部通过：5 个 user_tool 调通 + 27 自动化测试绿
- [ ] 容器 `docker compose up -d` 已起 + `check_stdio_server.sh` 通过
- [ ] Goose Desktop + OpenWork Desktop 都装好、配好 floorplan stdio extension（产品Spec §5.2/5.3）
- [ ] 准备好待测 DWG 放 `~/dwgs/`：至少含**参与者自己的图**1 张（不要只用合成图）
- [ ] ODA File Converter 装好挂载（产品Spec §1.2）
- [ ] 录屏工具开好（QuickTime / OBS）+ 知情同意书（截屏需许可）
- [ ] 把 `task-card.md` 打印或发参与者

---

## 2. 跑测流程（30-45 分钟）

| 时段 | 内容 | 主持动作 |
|------|------|---------|
| 0-3 min | 开场 + 知情同意 + 录屏许可 | 念 `task-card.md` 顶部说明 |
| 3-13 min | **T1 安装起步** | 计时；观察卡点；卡住超 5 分钟可给提示（记一笔） |
| 13-23 min | T2-T4 读图查询 | 让参与者主导；记录"AI 答对了吗 vs 图真实" |
| 23-35 min | **T5 改 + 撤销** | 核心任务；重点观察是否改坏、撤销能否回滚 |
| 35-43 min | **T6 自由探索** | "你想问它什么？" 鼓励乱花，记录误识别 / 触界 |
| 43-45 min | 5 问主观打分 | 念 `scorecard.md` 主观题 |

**关键主持原则**：
- 🤐 **不解释产品怎么用**（除了装好客户端后示范一句"在这里打字"）
- 🚫 **不替参与者点**（除非设备卡死）
- 📝 **记录原话**（用户失望/惊喜的瞬间比数据更值钱）
- ⏱️ **超时不要无限延长**（卡 5 分钟就给提示挪下一步）

---

## 3. 何时算"测完了"（每场结束条件）

满足以下任一：
- ✅ T1-T6 全跑完 + 主观打分
- ⏹️ T5 改图阶段出错且参与者明显失去信任（仍要记录主观分，但本次按"失败"打标）

---

## 4. 通过线（产品Spec §4.3 失败决策树）

汇总完 3-5 人后看（写 `aggregate.md`）：

| 维度 | 通过线 | 不过处置 |
|------|--------|---------|
| 任务完成率 | ≥ 80% | 回 Phase 1 调 backend/UX |
| **修改正确率（数据不破坏）** | **= 100%** | 🔴 红线失败：紧急加确认步骤 + 强化 .bak；不得进 Phase 2 |
| 主观满意度（5 分） | ≥ 3.5 | NL/反馈 UX 调优 |
| 安装摩擦中位数 | ≤ 2 次卡壳 | 改 install_oda.sh / Docker 镜像默认配 |

**🔴 修改正确率 100% 是硬红线**：错改 DWG = 用户数据破坏，是产品不可接受的故障。一次错改就停。

---

## 5. 报告产出（测完所有场后）

`aggregate.md` 填完后形成 1 页 V3 报告，含：
- 量化指标（4 个）
- 失败模式 top 5（哪些图/哪些话最常出错）
- 主观原话精选（≥5 条）
- Phase 2 必须解决项清单
- **决策**：通过 / 部分通过 / 不通过

把这份报告归档到 `floorplan-mcp/V3-round1-report.md`，进 Phase 2。

---

## 6. 常见主持陷阱（自检）

- ❌ 把"AI 答对"和"用户答对"搞混——要看**图真实情况**（用 CAD viewer 打开原图核对）
- ❌ 让参与者用我们的合成图（要用自己的图，摩擦才真实）
- ❌ 帮参与者把图先转换好（DWG→DXF 应让系统自己处理，否则没测到链路）
- ❌ 测完才打分（要在每任务结束后立刻打，主观分会磨损）
