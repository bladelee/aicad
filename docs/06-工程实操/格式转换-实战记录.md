## 0. 背景

- 核心任务：把 `dwg/*.dwg` 5 张真实别墅工程图（19-102 项目）转为 `.dxf`，才能让 ezdxf/FloorplanBackend 读入。
- DWG 版本分布（关键约束）：
  - R2007（2007-2009）— 2 张（4-立面图、5-节点）
  - R2010（2010-2012）— 1 张（1-封面/目录）
  - R2018+（2018-现在）— 3 张（2-材料表、3-平面系统图、XINLU-A2）
- R2018+ 是最新格式，**开源工具的兼容性最差**，必须事先验证。

## 1. 方案 A：ODA File Converter（已确认不可行 ❌）

### 1.1 方案期望
- ODA 是 DWG/DXF 转换的业界标准，免费（个人/教学），保真度最高。
- 用户已自行注册下载：
  - `~/Downloads/ODAFileConverter_QT6_macOsX_x64_15.0dll_27.1.dmg`（**需 macOS 13**，本机 12.7.6 跑不了）
  - `~/Downloads/ODAFileConverter_QT6_lnxX64_8.3dll_27.1.deb`（Linux 版可用，54MB）
  - `~/Downloads/ODAFileConverter_QT6_lnxX64_8.3dll_27.1.AppImage`（Linux AppImage，已下载，81MB）

### 1.2 5 步实验过程（每一步的具体破坏点）

| Step | 操作 | 结果 |
|------|------|------|
| ❶ | 用 ubuntu:22.04 装 `.deb` 试跑 | 可执行文件装到 `/usr/bin/ODAFileConverter`，但 `error while loading shared libraries: libGL.so.1` |
| ❷ | 加 libgl1 + xcb 依赖后重跑 | `qt.qpa.plugin: Could not load the Qt platform plugin "xcb"` |
| ❸ | `QT_DEBUG_PLUGINS=1` 看 Qt 自报原因 | **根因找到**：libqxcb.so 缺 `libxkbcommon-x11.so.0` 和 `libxcb-xkb.so.1` |
| ❹ | 补 libxkbcommon-x11-0 + libxcb-xkb1 后跑 | ODA 能启动，但**完全无动于衷**：5 分钟内不处理任何文件，DXF 目录空 |
| ❺ | 改用 AppImage（自带 Qt6 全套），加 Xvfb（虚拟 X server） | AppImage extract 成功，ODA 启动了 GUI 主窗口，等用户点 Convert 按钮；**CLI 参数被完全忽略** |

### 1.3 失败的根本结论

**ODA File Converter 27.1（2025）已移除真正的 CLI batch 模式。**

> 早期版本（≤25.x）的网上文档说"6 个 CLI 参数：源目录 目标目录 过滤器 输出版本 递归 审计"——这在 27.x **不再成立**。27.x 即使传参数也只是预填 GUI 表单，启动后停在主窗口等待用户点击。

证据：
- strings 二进制找不到任何 `usage` `argv` `--*` 字符串
- ODA 启动后进程 CPU 时间 0:00:00（没在干活）
- 容器日志只有 `QStandardPaths: XDG_RUNTIME_DIR not set`

### 1.4 教训与子发现（永久记忆）

1. **版本号要看准文档对应哪个 ODA 版本**：6 参数 CLI 用法存在于早期 ODA（≤25.x）。新版用法变了。
2. **Qt xcb 插件加载失败的真实报错路径**：开 `QT_DEBUG_PLUGINS=1` 让 Qt 自己说原因，不要凭印象猜库。
3. **Ubuntu 22 的 libxcb-util soname 坑**：旧引用 `libxcb-util.so.0`，系统装的是 `libxcb-util.so.1` → 需要 symlink（但实际不是核心问题，只是误导）。
4. **AppImage 在容器里能跑但需要 extract**：`<file>.AppImage --appimage-extract`，避开 fuse 依赖。
5. **ODA 是 Qt GUI 应用不是 CLI**：未来引入 ODA 系列，要假设它需要 X；用 `Xvfb :1 -screen 0 1024x768x24 -nolisten tcp -ac` +手动 export DISPLAY=:1。

### 1.5 ODA 仍可工作的场景（确认把这条路放弃）

外网资料 ODA 仍可在如下场景用：
- 装到本机 macOS 13+ / Windows / Linux 桌面环境 + GUI 点击
- 用 xdotool 自动化点击（脆弱，不推荐）
- 不放在 headless 容器时

→ 项目方向是 Docker 容器化（产品 Spec 要求），与 ODA GUI 模式不兼容。**完全放弃 ODA。**

## 2. 方案 B：LibreDWG（编译中，可行候选 ⏳）

 LibreDWG 是 GNU 项目，完全开源，免 EULA，DWG/dxf 双向转换的纯 CLI 工具。

### 2.1 方案期望

- `dwg2dxf <input.dwg> -o <output.dxf>` 一行命令
- 通过 `--disable-shared --enable-write` 编译出静态 binary
- 容器化使用方式与 ODA 不同：**libredwg 是纯命令行，无需 X**，跑起来非常轻量

### 2.2 编译路径（gradual 失败→成功）

第 1 轮 build：`.deb` 装依赖 `python3 swig` 让 configure 检测到 SWIG → configure 在 Python 链接选项上失败（"Could not link test program to Python"）。

```dockerfile
# 失败的 Dockerfile V1
apt-get install -y ... python3 swig ...   # ❌ 触发 Python dev 检测
./configure --disable-shared --enable-write
```

第 2 轮 build：加 `--disable-python --disable-perl`，再试。但 configure 又卡在 `git fetch --tags` 上——**国内访问 GitHub 拉取 tag 超时**，autogen.sh 无条件执行这一步。

```dockerfile
# 失败的 Dockerfile V2
&& sh autogen.sh   # ❌ 内部跑 git fetch --tags，国内 GitHub 慢，永久 hang
```

第 3 轮 build（**当前进行中 ✅**）：直接 patch autogen.sh 移除 git fetch，并预填 `.version` / `.tarball-version` 让 git-version-gen 不再需要 git。

```dockerfile
# ✅ 工作的 Dockerfile V3（关键片段见 dwg/Dockerfile.libredwg）
&& git clone --depth 1 --no-tags https://github.com/LibreDWG/libredwg.git \
&& cd libredwg \
&& echo "0.14.8566" > .version \
&& echo "0.14.8566" > .tarball-version \
&& sed -i '/git fetch.*tags/d' autogen.sh \
&& sh autogen.sh \
&& ./configure --disable-shared --enable-write \
               --disable-python --disable-perl --disable-examples \
&& make -j"$(nproc)"
```

### 2.3 已成功的子步骤

| 时间点（秒） | 进度 |
|------|------|
| 0–8 | git clone（GitHub 通；非 tag 拉 tag） |
| 8–60 | autogen + libtoolize（移除 fetch 后正常） |
| 60–145 | configure 探测 |
| 145–490 | 第一批 CC：print / free / hash / classes / dwg_api / geom / out_dxf / out_json / encode 等 |
| 490–760 | 第二批 CC：encode2 / dxfclasses / in_dxf / in_json / dynapi |
| 760+→应该 | `make[4]: Leaving directory` → `make[3]` → `make[2]` → `make install` |

### 2.4 LibreDWG 已知缺陷

| 缺陷 | 影响 |
|------|------|
| R2018+ DWG 解析不如 ODA 完整 | 3 张 R2018+ 图可能丢失部分字段（MTEXT 高级属性、动态块） |
| 不支持 ODA 的 audit/repair | 写工具前需要更注意源文件完整性 |
| 编译耗时 5-15 分钟 | 一次性代价，未来镜像缓存命中可省 |

预期：3 张 R2007/R2010 的图应能 100% 转；3 张 R2018+ 转出 80-95% 字段（足够 ezdxf 读入做房间/家具识别）。

### 2.5 教训

1. **libredwg autogen.sh 强制网络访问，国内必须 patch**
2. **必须 `--disable-python --disable-perl` 避免 swig dev 依赖**
3. 用 **`docker system df` 看 "Build Cache ACTIVE=N"** 判断 buildkit 是否真的在编（比反复 tail log 准）

## 5. 教训总结与最佳实践

### 5.1 教训 1：**优先确认工具的"命令行模式"真实存在**

不要被网上旧文档误导。CLI 工具可能在新版本中**变成纯 GUI**。验证步骤：
```bash
# 1. 看 binary 是否真有 CLI 标志
strings <binary> | grep -iE "usage|argv|--"

# 2. 跑 --help 短超时
timeout 5 <binary> --help

# 3. 看启动后是否真的处理输入（看 CPU 时间是否增长）
<binary> ... &
sleep 5; ps -o %cpu,time $!
```

### 5.2 教训 2：**Qt GUI 应用怎么跑 headless**

```bash
# 1. 装 Qt xcb 全套依赖（具体包名按二进制要求）
apt-get install -y libgl1 libxkbcommon-x11-0 libxcb-xkb1 libxcb-cursor0 ...

# 2. 启 Xvfb 虚拟 X server，关鉴权
rm -f /tmp/.X1-lock /tmp/.X11-unix/X1
Xvfb :1 -screen 0 1024x768x24 -nolisten tcp -ac &
sleep 2
export DISPLAY=:1
export XAUTHORITY=    # 空，让 -ac 接管

# 3. 用 QT_DEBUG_PLUGINS=1 找缺啥库
QT_DEBUG_PLUGINS=1 <app>
```

### 5.3 教训 3：**编译依赖网络时必须避开 tag 拉**

GNU / autotools 项目的 `autogen.sh` 经常含 `git fetch --tags`，国内网络对 GitHub tag 服务器特别慢。**通用做法**：
```bash
sed -i '/git fetch.*tags/d' autogen.sh
echo "1.2.3" > .version            # 预填版本号给 git-version-gen
echo "1.2.3" > .tarball-version
```

### 5.4 教训 4：**`docker build | tail -N` 是隐形陷阱**

`make -j$(nproc)` 多核并行会让 make 输出乱序/缓冲，`| tail -N` 看不到中间进度。
**正确策略**：`docker build ... | tee /tmp/build.log | tail -N`，再单独 `tail -f /tmp/build.log` 看，或者看 `docker system df` 的 Build Cache ACTIVE。

### 5.5 教训 5：**Docker bind mount 的"`.`开头隐藏目录"坑**

`.oda_pkg` 在 macOS Docker Desktop 下，曾在容器里见不到（可能因早期 mount 的失败 cache）。**改名 `oda_pkg`（无 . 前缀）后正常**。
**排查方法**：
```bash
docker run --rm -v "$PWD:/data" ubuntu ls -la /data/
# 对比宿主机 ls -la
```

### 5.6 最佳实践（沉淀）

1. **DWG 转换路径优先级（永久记忆）**：
   - 桌面环境 ODA GUI ✓
   - libredwg 容器编译 ✓ （开源）  
   - ODA headless ✗（27.x 不行）
   - ezdxf 直读 ✗（开源版无 ODA SDK）
2. **优先固化镜像**：不要每个 `docker run` 都 apt install 一遍依赖，固化到镜像，未来转换秒级。
3. **写 Dockerfile 时永远附 fallback**：源码编译失败 → 准备好 .tar.gz 静态包路径。
4. **小步前进**：每个 make 步骤独立 RUN，便于定位失败层。

## 7. 待执行清单（编译完成后立即跑）

```bash
# 1. 等 libredwg-cli 镜像 build 完成（看 docker images libredwg-cli）

# 2. 一行命令转所有 DWG 到 DXF
docker run --rm -v "$PWD/dwg:/data" libredwg-cli -y -o /data/dwg/dxf/<name>.dxf /data/dwg/<name>.dwg
# 或循环：
for f in dwg/*.dwg; do
    out="dwg/dxf/$(basename "${f%.dwg}").dxf"
    docker run --rm -v "$PWD:/data" libredwg-cli -y -o "/$out" "/$f"
done

# 3. 扫描产出关联图谱（在 floorplan-mcp 容器内跑 scan_dxf.py）
docker run --rm -v "$PWD:/data" \
    -e PYTHONHOME=/opt/FreeCAD/usr \
    -e LD_LIBRARY_PATH=/opt/FreeCAD/usr/lib \
    -e SSL_CERT_FILE=/opt/FreeCAD/usr/ssl/cacert.pem \
    --entrypoint=/bin/bash \
    floorplan-mcp:latest \
    -lc "/opt/FreeCAD/usr/bin/python /data/dwg/scan_dxf.py"
```
