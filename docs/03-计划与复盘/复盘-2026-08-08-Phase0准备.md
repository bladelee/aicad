## 三、已解决的问题（关键 bug / 错判 / 缺口）

按"如果没发现，会进 Phase 1 才爆"的严重度排序：

### P0 — 招牌功能地基错（v1 阶段）

- **v1 房间识别算法不成立**：用"闭合 lwpolyline = 房间"，但真实图纸墙体是独立 LINE 段，会识别 0 房间。
  - **解决**：换成 shapely polygonize（planar-graph face detection）
  - **验证**：合成 3 房间图，v1 算法得 0，shapely 精准得 3
  - **教训**：先合成测试样本验证算法可行性，别等真实样本（Phase 0 前移到代码期）

### P0 — 写工具安全层（R2）

- **freecad-ai user_tools handler 不走 `_with_undo`**：实读源码（`extensions/user_tools.py::_make_handler`）发现设计文档说了"包 undo transaction"但代码没兑现。
  - **解决**：自写 `backends/_safety.py::with_transaction` + `make_backup`，写工具自带 transaction + .bak
  - **教训**：第三方库的设计文档 ≠ 实现现状，**关键安全依赖必须实读源码确认**

### P0 — 跨平台 transport 误解（D → E → F）

- 误判"freecad-ai 是 Linux entry = FreeCAD 不能在 Windows 跑"（D 错判）
- 误判"F 默认 SSE server 在 Goose 可用"（产品Spec 初版）
  - **解决（D→E→F）**：Docker 容器化一举绕开平台问题 + freecad-ai entry 在 Linux 容器内原样可用
  - **解决（SSE→stdio）**：实读 Goose `ExtensionConfig` 源码发现 SSE 已废弃，MVP 选 stdio 单通道
  - **教训**：调研第三方 provider 的兼容性**要看源码枚举/常量**，不能只看文档示例

### P1 — 房间识别 bug（freecad_backend 只识别 1 房间）

- v0 骨架用 `Arch.makeSpace([所有墙])` 只产生 1 个总空间
  - **解决**：抽共享算法 `backends/rooms_detect.py::detect_rooms`，主备 backend 同源，房间数永远一致
  - **附加价值**：消除了"换 backend 房间数对不上"风险
  - **教训**：两个 backend 共用的能力**必须抽到单一真源**，否则一双实现两套 bug

### P1 — 关键词分类 bug（`BED_1800` 被判为门）

- `DOOR_KEYWORDS` 含 `"D_"`，命中 `BE**D_**1800`
  - **解决**：`_classify` 先匹配细粒度家具类型，门/窗兜底
  - **教训**：**测试是兜底**——单测当场抓出此 bug；有了 lint 后改不会回归
  - **教训**：短前缀关键词（如 `D_` `W_`）天然脆弱，Phase 1 必须升级三维特征分类

### P1 — 跨平台 fd 重定向（stdio 入口）

- freecad-ai 自带的 `mcp_server_entry.py` 用 bash `exec 3>&1 1>&2`（Linux/macOS 专属）
  - **解决**：自写 `mcp_server_stdio.py`，用 Python 原生 `os.dup2` 实现等价效果，跨平台（Windows 容器也跑）
  - **教训**：能跨平台就别依赖平台专属 shell 技巧

### P2 — docstring 不规范（影响 LLM 路由）

- 初版 user_tool docstring 只 1-2 行，没有"何时不用"，LLM 容易乱调
  - **解决**：产品Spec §3.4 定模板（"适用 + 不要用于 + 用户口语 ≥3 条 + Args"）写到 docstring，lint 钉死
  - **教训**：MCP 工具的 description 决定 LLM 路由准确率，必须**像写产品 UI 文案一样郑重**

### P2 — Phase 0 房间识别准确率没自动算法

- 最初脚本只识别房间数，留给"人工对照"模糊
  - **解决**：脚本自动写 `manual_template.md` → 设计师填 → 回读 `manual_answers.json` 算 R1 匹配率 + 面积误差
  - **两轮端到端验证通过**（合成样本模拟 100% 准确率）
  - **教训**：自动化脚本要考虑"人介入"的接缝——脚本生成模板、人填、脚本回读，闭环

### P2 — 文档版本/交叉引用不一致

- v1.0 产品Spec 一处写 stdio 推荐另一处推 streamable_http，自相矛盾
  - **解决**：v1.1 全局对齐 MVP stdio + 交叉引用 sanity 检查
  - **教训**：方案演进时**别只改决策章节，要把全文矛盾点一次性扫干净**；用 grep 跨文件确认 transport 含义一致

## 四、经验教训（按主题）

### 4.1 决策方法

1. **不要相信印象，相信源码**：调研 provider/依赖时，看 `ExtensionConfig` 枚举、`_make_handler` 实现、`tests/integration/conftest.py` 用的真实跑法 —— 这些是 ground truth。文档/README 经常滞后或营销。
2. **否定方案要给证据**：v1 → A → B → C → D → E → F 这条演进链上每个"否决"都附了实读源码或运行证据，避免后面有人凭印象复活坏方案。
3. **用户每改一次约束，全链 re-evaluate**：从"全栈在一个机器" → "混合架构" → "Docker 化" → "Goose/OpenWork 前端" 等约束，每次都重做了决策矩阵。**别带着旧约束写新方案**。

### 4.2 备选方案设计

1. **共享不变的部分**（减少维护）：主备 backend 的差异只在最贵能力（房间识别），其余共享。我们抽到 `rooms_detect.py` 单一真源就是这个原则。
2. **接口抽象让备选可热切换**：`FloorplanBackend` Protocol + `FLOORPLAN_BACKEND` env 切换，切后端零代码改。
3. **诚实标注共同单点**：ODA EULA 是所有方案都过不去的，**显式标"无法靠架构消除"，给合规处置路径**（不打包 + 引导安装）。

### 4.3 KISS / 精益

1. **MVP 别同时做 3 个 transport**：stdio 单通道起步，streamable_http 推 Phase 1.5。一次同时做 3 个是"非必要的难度"。
2. **测试用合成样本就能验证算法**：房间识别、shapely polygonize 这些不必等真实 DWG。**合成 7 边界用例就够发现明显 bug**。
3. **不写过度功能**：v1 有 13 种家具块工厂，砍掉只留 door/window——真实图纸自带块库。

### 4.4 测试

1. **测纯函数最容易立竿见影**：`_safety`、`_classify`、`detect_rooms` 都是纯函数 + 单测，第一轮就抓 bug。
2. **测试本身也会错**：写过 `capsys` 测底层 fd 重定向（pytest 替换 Python 层 sys.stdout，跟 fd 不通），改成 os.pipe 直测才对。**测试失败先想"是不是测试自己错"**。
3. **lint 类测试防漂移**：docstring 模板用 lint 钉死，description 漂移立即挂 —— 比代码 review 强制。

### 4.5 工具协作

1. **miniconda3 Python 替坏的系统 python3**（Xcode 残留）让本机能跑测试，不用等容器。
2. **memory 沉淀调研结论**：freecad-ai / 前端的"硬事实"写到 `/memories/repo/*.md`，下次方案迭代不用重新调研。
3. **ops/ 目录的 system-info 给了现状真值**：Docker 17.12 + Compose 1.18 太老，避免空想。
