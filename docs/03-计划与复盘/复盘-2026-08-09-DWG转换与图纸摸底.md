## 二、最关键的 4 个发现

### 2.1 🔴 真实发现 1：ODA 27.x 已无 CLI 模式

历史上 ODA File Converter 网上文档说的"6 参数 CLI batch 模式"在 27+ 版本不再成立。**实际证明**：
- 27.x 是纯 GUI 应用
- 命令行参数只是预填表单，启动后停在主窗口等用户点击 Convert
- 头 files binary 找不到任何 `usage/argv/--*` 字符串

**教训**：网上文档要分清对应的工具版本，"6 参数"对应的是 ≤25.x 早期 ODA。

### 2.2 🔴 真实发现 2：图纸是「天正建筑」画的

扫描发现块名前缀含 `$TCHSYS$` `$TwtSys$` `$WINLIB2D$`—— 这是天正建筑（TArch）软件的标志。

**意味着**：
- 墙/门窗/家具是天正自定义对象，不是 std LINE/POLYLINE
- 转 DXF 后这些对象变成 **PROXY 实体 + XData**
- ezdxf 读到的是空壳代理，**几何信息全在 XData 里**
- **改墙任务比预想难 1 个量级**（要先解码 XData 才能拿到墙的几何边界）

### 2.3 🟡 真实发现 3：2 张图扫出 0 实体

`1-封面、目录、设计说明` 和 `2-材料表` 的 modelspace 实体数为 0：
- 真实内容全在 **paper space (Layout1 / 布局1 / 布局2)** 里
- scan_dxf.py 只扫了 modelspace，所以漏了所有封面+材料表+目录数据
- 用户要求 #6（材料表 ST-01 → ST-A 联动）的核心数据**当前扫描不到**

### 2.4 ✅ 真实发现 4：跨图强关联锚点

126 个公共图层 + 273 个公共块中，最有价值的几个：

| 图层/块 | 共享范围 | 业务意义 |
|---------|---------|---------|
| `A原建筑墙体` | 平面+立面+节点 | 改墙任务核心锚点 |
| `A原建筑外幕墙，门，窗` | 平面+立面+节点 | 门宽变更 |
| `A原建筑尺寸` | 平面+立面+节点 | 标注顺改 |
| `A图框` | 材料表+平面 | 编号/目录 |

**意味着改墙任务有清晰的"主链路"**：改 `A原建筑墙体` 一个图层，能联动到 3 张图。

## 三、踩过的坑（5 个 + 1 个本机环境问题）

### 坑 1：ODA 27.x vs 早期文档不一致
- **现象**：网上说 6 参数 CLI，实测完全无效
- **根因**：版本变化，27.x 是 GUI-only
- **解法**：放弃 ODA，转 libredwg

### 坑 2：本机 brew 损坏（连带 Xcode）
- **现象**：brew install libredwg 失败
- **根因**：用户本机 Xcode.app 是旧版（升级时残留），dyld 找不到 libauto.dylib
- **解法**：用户主动跑 `xcode-select --install` 装 CLT，恢复 git 工具

### 坑 3：Ubuntu 没现成 libredwg apt 包
- **现象**：`apt install libredwg-tools` 报 package not found
- **根因**：libredwg 不在 Ubuntu jammy universe 主仓库
- **解法**：必须从源码编译

### 坑 4：libredwg autogen.sh 强制 `git fetch --tags` 在国内 hang
- **现象**：编译到 `git fetch --tags` 永久卡住
- **根因**：国内访问 GitHub tags 服务器超时
- **解法**：`sed -i '/git fetch.*tags/d' autogen.sh`，并预填 `.version` `.tarball-version`

### 坑 5：libredwg configure 默认探测 SWIG Python 绑定失败
- **现象**：configure 报 "Could not link test program to Python"
- **根因**：装了 `python3 swig` 配过，但没装 Python dev 库
- **解法**：`--disable-python --disable-perl --disable-examples`

### 坑 6：Docker bind mount 看不到 `.oda_pkg` 隐藏目录
- **现象**：宿主机有 `.oda_pkg`，容器里 `ls` 不到
- **根因**：早期 docker mount 的失败 cache
- **解法**：改名去 `.` 前缀（`mv .oda_pkg oda_pkg`）

## 五、教训（针对项目长期）

### 教训 1：**早期方案应直接动手做一个最小可工作 demo**

ODA 在国内开发者社区的口碑很好，所以一开始就想用。但**一开始应该先用 5 分钟跑一个最小测试** —— 比如先看 binary 是不是真有 CLI 标志，先打 ODA 5 个参数看响应。如果一开始就发现 ODA 27.x 不响应 CLI，能省 2 小时。

### 教训 2：**网络敏感的构建步骤必须固化**

国内 Docker build 卡在 `git fetch --tags` 是常见的坑。**所有依赖网络拉取的 Dockerfile 步骤**（git clone / curl / wget）都应有：
- 国内 mirror fallback
- 标记版本号（不靠 fetch tags）
- 超时退出（不让 build 永久 hang）

### 教训 3：**用户给的样本要先扫一遍基础结构再设计**

如果第一天就跑 scan_dxf.py 看一眼图纸结构，会立刻发现：
- 这是天正图（影响后续所有改图任务）
- 封面/材料表是 paper space（影响扫描覆盖范围）

**特殊行业工具的图纸**（天正/中望/浩辰）跟纯 AutoCAD 处理方式完全不同。

### 教训 4：**目录组织应该和数据规模一起设计**

5 张真实图带来的文件量（原始 DWG + 转换 DXF + 报告 + 多个测试脚本）很快就让 `dwg/` 目录爆炸。**项目初期就该分清**：
- 原始数据（只读）
- 中间产物（programs 写）
- 文档（人写）
- 工具脚本（github 风格管理）

详见 `docs/目录整理方案.md`。

### 教训 5：**Headless 容器跑 GUI 工具是个糟糕起点**

ODA 是 GUI 工具，我尝试用 Xvfb 在容器里跑。但即使能跑通也是脆弱的—— 任何 Qt xcb 库升级、X 鉴权变化都可能 break。**应该首选原生 CLI 工具**（如 libredwg）。
