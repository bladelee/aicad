## 二、#2 内自洽的 2 条升级路径（决策点）

MVP 当前是"半径 2000mm 整体平移"，有 3 个理论缺陷：

| 缺陷 | 影响 | 严重度 |
|------|------|------|
| 半径内**跨房间**实体也会被联动 | 错改 | **高** |
| 整体平移而非**边界匹配** | 真实业务里墙端点延伸应触发地坪线重画 | 中 |
| 未联动 **DIMENSION** 标注值 | 数字不对 | 高 |

### 🔴 路径 B：shapely 空间分区（建议产品化首选）

**目标**：把"附近 2000mm"换成"被改墙包围的同一空间内才联动"。

**算法**：
1. 用 shapely 的 [`polygonize`](tools/dxf_scan/../dxf_edit/move_wall.py) 把所有墙线构 planar graph
2. 每个面（face）= 一个房间
3. 改墙时识别"墙两侧的两个房间"
4. 只对这两个房间内的地坪/天花实体做联动

**复用资产**：`memories/repo/freecad-ai-findings.md` 里 v1 房间识别算法已被 `backends/rooms_detect.py` 用 shapely polygonize 实现过（合成 3 房间图上得分 3/3）—— 这块代码可**直接复用**。

**工作量**：半天（含用真实 3-平面图回归验证）。

**收益**：消除"跨房间错联动"，演示说服力大幅提升。

**风险**：
- 真实平面图比合成样本复杂（多内墙、弧形墙），polygonize 召回率不保证 100%
- 建议：演示前用 wall_idx=6 (E6037) 那条墙**人工验证一次**，看 polygonize 输出的房间是不是合理的。

### 🟠 路径 C：DIMENSION 重算（独立算法工作）

**目标**：改墙后，关联的 DIMENSION 实体的标注值自动重算。

**算法**：
```python
# DIMENSION 实体的关键属性：
# DEFPOINT (defpoint)        — 标注起点
# DEFPOINT2 (defpoint2)      — 标注终点
# DIMSTYLE (dimstyle)        — 标注样式
# 实际标注文本 (entity.text)  — "<>" 表示用 measurement 默认值

# 改墙流程：
# 1. 找 DEFPOINT / DEFPOINT2 落在改墙端点 ± 500mm 内的 DIMENSION
# 2. 把 DEFPOINT 重新指到新的墙端点
# 3. 重算距离 measurement = dist(defpoint, defpoint2)
# 4. 如果 entity.text == "<>" 则 measurement 自动生效
#    如果 entity.text 是硬编码（"5700"），需要字符串替换
```

**复用资产**：无现成的，但 `tools/dxf_edit/apply_material_rename.py` 的"INSERT attribs 替换"算法可以借鉴 — DIMENSION 的 text 字段处理类似。

**工作量**：1-2 天（含 DIMSTYLE 样式系统调研 + 文本重算 + round-trip 验证）。

**收益**：解锁 #3 的硬骨头（"完全匹配"的核心 = 标注数字与几何一致）。

**风险**：
- DIMSTYLE 在不同 CAD 软件下表现不同
- AutoCAD DIMENSION 可以是 ALIGNED / LINEAR / ANGULAR 等多种类型，每种重算逻辑不一样
- 真实图里可能用 PROXY DIMENSION（被 libredwg 转换降级）

### 🟡 何时做哪条

```
MVP 演示前  → 不动当前算法（已能演示）
演示后如果客户要求真实精度 → 路径 B（半天）→ 路径 C（1-2 天）
真上生产前  → B + C 都做完
```

## 三、跨视图（#4/#5/#9）的产品化路径

MVP 路径已通（基于 Z 索引块编号指针），但有 2 个待解决：

### 3.1 在 5-节点里找含相同编号的实体

**问题**：3-平面 Z节点索引 attrib `1EA-07=DE-02` → 指向 5-节点里的编号 DE-02。但 **5-节点里怎么找带 DE-02 标识的实体？**

**实测**：5-节点里 `Z节点索引` 图层是空的 `{}` — 没有反向指针。

**3 种候选实现**：
1. **TEXT/MTEXT 全图搜**：找含 `DE-02` 字串的 TEXT — 范围广但可能有误命中
2. **图框标题字段**：5-节点的 Layout1 标题栏里有"图号"字段，可能就是 DE-02
3. **空间坐标聚类**：5-节点 里若干个小节点区域，每个区域开始处可能有一个大号的 DE-XX 标题 TEXT

**建议方案**：先做 (1) 全图文本搜，看精度够不够。

### 3.2 跨图坐标变换矩阵

**问题**：3-平面 墙在 (206902, -908615)，对应 5-节点 区域中心在 (?, ?)？这两个坐标如何对应？

**算法**：
```python
# 通过 Z 节点索引块定义"对应关系"
# 1. 从 3-平面 Z节点索引 INSERT 的 insert (cx, cy) = 平面坐标
# 2. 在 5-节点 找含相同编号 DE-02 的 TEXT 的 insert (nx, ny) = 节点坐标
# 3. 计算 offset = (nx - cx, ny - cy)
# 4. 后续这个编号内的所有改造都用这个 offset 做坐标变换
```

**工作量**：2 小时（含 probe）。

**收益**：解锁 #4 / #5 / #9 跨图改造的算法根基。

## 六、Phase D：从零生图（借鉴 wheel-drawing-tools 的产品拓展方向）

> 详见 `docs/借鉴-wheel-drawing-tools-参数化模式.md`（含完整对照分析 + 3 个核心模式 + 2 处可直接照抄代码）

### 6.1 业务定位（与前三阶段的边界）

| 阶段 | 业务模型 | 工作模式 |
|------|------|------|
| Phase A (MVP 验证) | 改局部 → 联动验证链路通 | `ezdxf.readfile → 改局部 → saveas` |
| Phase B (产品化) | 把 MVP 的近似算法升级为空间感知 | shapely + DIM 重算 |
| Phase C (跨视图) | 多张图编号联动 | 基于 `DE-XX`/`1EA-XX` 指针 |
| **Phase D (从零生图)** | **输入参数 → 一键生成图纸** | `ezdxf.new → 表达式绘制 → saveas` |

→ Phase D **不替换前三阶段**，是新增的独立能力。适合**新户型从样板间快速出图**场景，与"老图改"互补。

### 6.2 借鉴 wheel-drawing-tools 的 3 个核心模式

| 模式 | wheel 项目怎么做 | 我们怎么做 |
|------|------|------|
| 1. 图形定义+参数双层 | `shape_definition=[{"type":"rect","width":"L"}], parameters=[{"param_name":"L"}]` | 套用于"墙 + 门 + 窗 + 家具"标准模块，参数化冲生成全新户型 |
| 2. `_eval_expr()` 表达式求值 | `re.sub + eval(s, {"__builtins__":{}}, {"cos":...,"sin":...,"pi":...})` | 立即抄到 `tools/dxf_edit/`，让现有 `shift_layer_entities` 也支持表达式坐标 |
| 3. `flatten_shapes(scale, dx, dy)` | 求值后整体平移到目标视口 | 用在 #4/#5/#9 把改过的墙叠加到立面/节点视图 |

### 6.3 wheel 项目 2 处可直接照抄的代码

| 代码 | 来源文件 | 用途 | 落地到我们哪里 |
|------|------|------|------|
| `_eval_expr() + _get_num()` | `drawing_engine.py` | 表达式驱动的坐标计算 | `tools/dxf_edit/param_expr.py`（✅ 已落地）|
| `_doc_to_shapes()` | `cad_dxf.py` | 把 DXF 文档反向提取为统一图形 dict 列表 | `tools/dxf_scan/doc_to_shapes.py`（新建，替换散在 probe 脚本里的代码）|

### 6.4 不能直接复用的地方（差异点，永久记忆）

- wheel 用 `ezdxf.new()` 从零生成；我们前 3 阶段**必须 `readfile` 保老图所有非改造实体**
- 跨视图关联：wheel 用 `flatten + dx/dy` 简单拼；我们靠 `DE-XX` 编号指针
- 复杂度：标准钢轮几十个图形 vs 装修图 9000+ 实体

→ Phase D 适合**特定场景**（生成标准模块、装到老图里），不能完全替代老图改造路径。
